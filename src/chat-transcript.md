## Codex

Посмотрел [README.md](C:/school21/ML4_Classification_problems_ID_1254802-1/README.md). Это хороший учебный проект по бинарной классификации. Сначала строишь базовые модели на `sklearn`, затем реализуешь Logistic Regression, Gaussian Naive Bayes и KNN с нуля и проверяешь, насколько близки результаты. Самая содержательная часть задания — честно сравнить модели на данных из будущего.

В практической части я бы обратил внимание на четыре места.

- **Разбиение по датам.** «Первая треть дат» я бы трактовал как первую треть отсортированных уникальных `PurchDate`. Тогда записи за один день целиком попадут в одну выборку, как и требует строгое неравенство между периодами. Доли строк при этом могут отличаться от ⅓.
- **Утечка при создании признаков.** В шаге 7 пример с `groupby` легко скопировать на весь датасет. Средние по группам, заполнение пропусков, кодирование и масштабирование нужно рассчитывать на train и затем применять к validation и test.
- **Неоднозначные метрики.** Для Gini в шаге 5 явно просят свериться с `abs(2 * ROC AUC - 1)`. Модуль может скрыть перепутанный порядок классов, поэтому полезно вывести рядом и сам ROC AUC, рассчитанный по скору класса `IsBadBuy=1`. Для «AUC PR» стоит явно указать, что именно считаешь. README подводит к Average Precision, а площадь под PR-кривой по трапециям может дать другое число.
- **Роль test.** В шаге 10 на test оцениваешь уже выбранную модель, а в шаге 11 сравниваешь на нём алгоритмы. Это совместимо, если зафиксировать все сравниваемые варианты по validation до первого обращения к test. Если результат на test ниже, одного этого недостаточно, чтобы заключить, что модель переобучилась. При временном разбиении могли измениться и сами данные.

Я бы начал с разбиения, общего препроцессинга и таблицы результатов трёх моделей `sklearn` на validation. По README достаточно, чтобы **хотя бы одна** из них набрала Gini ≥ 0.15. Эта таблица затем станет точкой отсчёта для самописных моделей, новых признаков и отбора признаков.

## Codex

В [training.csv](C:/school21/ML4_Classification_problems_ID_1254802-1/src/data/training.csv) **72 983 строки и 34 столбца**. Целевой класс `IsBadBuy=1` встречается в **8 976 строках (12,30%)**. Если всегда предсказывать `0`, accuracy уже будет 87,70%, поэтому для сравнения моделей здесь полезнее смотреть на Gini и Average Precision.

Разбиение по третям отсортированных уникальных `PurchDate` даёт такую картину:

| Выборка | Период | Строк | `IsBadBuy=1` |
|---|---|---:|---:|
| Train | 05.01.2009–01.09.2009 | 23 059 | 11,31% |
| Validation | 02.09.2009–30.04.2010 | 24 104 | 13,29% |
| Test | 03.05.2010–30.12.2010 | 25 820 | 12,26% |

Доля проблемных машин меняется между периодами. Это стоит учитывать при сравнении Average Precision и метрик при фиксированном пороге.

Для первого прогона я бы подготовил признаки так:

- **Убрал `RefId` из признаков.** Он уникален для каждой строки и может случайно передать модели порядок записей. `BYRNO` и `VNZIP1` я бы кодировал как категории, хотя в CSV они записаны числами.
- **Отдельно обработал пропуски.** В `PRIMEUNIT` и `AUCGUART` по **95,32%** пропусков. Для базовой модели их можно отложить, а затем проверить на validation, полезен ли сам факт наличия значения. В `WheelType` около 4,35% пропусков, в `Trim` — 3,23%.
- **Учёл размер категорий.** В `Model` 1 063 разных значения, в `SubModel` — 864. Полный one-hot заметно расширит матрицу, особенно для `GaussianNB`, которому нужен плотный вход, и для KNN, которому придётся считать расстояния. Для первого сравнения можно объединить редкие категории, определяя их частоты только на train.
- **Проверил доступность `MMRCurrent*` на момент покупки.** По CSV нельзя установить, когда были рассчитаны эти оценки. До выяснения я бы начал с `MMRAcquisition*` и попробовал признак `VehBCost / MMRAcquisitionAuctionAveragePrice` — насколько цена покупки отличается от аукционного ориентира.

## Codex

Каждая строка в [training.csv](C:/school21/ML4_Classification_problems_ID_1254802-1/src/data/training.csv) — это **покупка подержанного автомобиля на аукционе**. В таблице есть характеристики машины (марка, модель, год, пробег), детали сделки (дата, аукцион, цена покупки) и рыночные оценки стоимости.

Главный столбец — **`IsBadBuy`**. `1` означает, что покупку признали проблемной, `0` — что её к таким покупкам не отнесли. Например, после покупки мог обнаружиться скрученный пробег, серьёзная неисправность или проблема с документами, из-за которой машину трудно перепродать. Метка показывает итог сделки, а конкретная причина в ней не указана. [Описание соревнования на Kaggle](https://www.kaggle.com/competitions/DontGetKicked)

Например, в первой строке — Mazda 3 2006 года, купленная на аукционе ADESA за $7 100. У этой сделки `IsBadBuy=0`.

**Смысл задачи** — по прошлым сделкам научиться заранее оценивать риск проблемной покупки. Если модель ставит конкретной машине высокий риск, дилер может внимательнее проверить её перед ставкой.

## Codex

В [training.csv](C:/school21/ML4_Classification_problems_ID_1254802-1/src/data/training.csv) каждая строка описывает покупку подержанного автомобиля на аукционе. Вот что означают все 34 столбца. Названия сохранены как в CSV. [Описание данных Kaggle](https://www.kaggle.com/competitions/DontGetKicked/data)

### Сделка и её результат

| Столбец | Что означает |
|---|---|
| `RefId` | Уникальный идентификатор записи. |
| `IsBadBuy` | Целевая метка. `1` — покупку признали проблемной, `0` — её не отнесли к проблемным. |
| `PurchDate` | Дата покупки в формате месяц/день/год. Например, `12/7/2009` — 7 декабря 2009 года. |
| `Auction` | Аукционная площадка, например `ADESA` или `MANHEIM`. |
| `BYRNO` | Идентификатор покупателя, который приобрёл автомобиль на аукционе. |
| `VNZIP1` | Почтовый ZIP-код места покупки. |
| `VNST` | Код штата, где купили машину. Например, `FL` — Флорида. |
| `VehBCost` | Фактическая цена покупки автомобиля в долларах. |
| `IsOnlineSale` | Канал покупки. `1` — через интернет, `0` — офлайн. |

### Характеристики автомобиля

| Столбец | Что означает |
|---|---|
| `VehYear` | Модельный год автомобиля. |

### Рыночные оценки стоимости

Восемь полей `MMR…` — ценовые ориентиры. Их имена сочетают **момент оценки** (`Acquisition` — при покупке, `Current` — на дату актуальной оценки), **рынок** (`Auction` — аукционный, `Retail` — розничный) и **состояние** (`Average` — среднее, `Clean` — выше среднего). Точная дата для `Current` в CSV отдельным полем не указана. [Расшифровка полей Kick Cars](https://rstudio-pubs-static.s3.amazonaws.com/1021262_c95837b3790b4fd2b9e1dd917f5799c5.html)

| `MMRAcquisitionRetailAveragePrice` | Розничная оценка при покупке для среднего состояния. |
| `MMRAcquisitonRetailCleanPrice` | Розничная оценка при покупке для состояния выше среднего. В имени столбца в CSV пропущена буква `i` в `Acquisition`. |
| `MMRCurrentAuctionAveragePrice` | Актуальная аукционная оценка для среднего состояния. |
| `MMRCurrentAuctionCleanPrice` | Актуальная аукционная оценка для состояния выше среднего. |
| `MMRCurrentRetailAveragePrice` | Актуальная розничная оценка для среднего состояния. |

### Спрос и гарантии

| Столбец | Что означает |

## Codex

Для первого прогона я бы сделал **один общий препроцессинг для Logistic Regression, GaussianNB и KNN**. Сначала раздели сделки по времени, затем настрой все преобразования на train. Так результаты трёх моделей можно будет сравнить на одинаковых признаках.

### 1. Раздели данные по `PurchDate`

Прочитай `PurchDate` в формате `%m/%d/%Y`, отсортируй **уникальные даты** и разбей их на три последовательные части. Все покупки за один день должны попасть в одну выборку.

| Выборка | Период | Для чего |
|---|---|---|
| Train | 05.01.2009–01.09.2009 | Настроить препроцессинг и обучить модели |
| Validation | 02.09.2009–30.04.2010 | Сравнить модели, признаки и гиперпараметры |
| Test | 03.05.2010–30.12.2010 | Оценить зафиксированные модели в конце |

### 2. Определи, какие столбцы пойдут в модель

- **Цель** — `IsBadBuy`. Отдели её от признаков.
- **Служебные поля** — исключи `RefId`, а `PurchDate` используй для разбиения. Для первого прогона хватит `VehicleAge` как признака возраста машины.
- **Числовые признаки** — например, `VehicleAge`, `VehOdo`, `VehBCost`, `WarrantyCost` и `MMRAcquisition*`.
- **Категории** — например, `Auction`, `Make`, `Model`, `Trim`, `SubModel`, `Transmission`, `VNST`. `BYRNO` и `VNZIP1` тоже категории, хотя выглядят как числа. Из `WheelType` и `WheelTypeID` я бы оставил `WheelType`.
- **Поля для отдельного эксперимента** — `PRIMEUNIT` и `AUCGUART`, у которых по 95,32% пропусков. `MMRCurrent*` я бы отложил, пока не ясно, были ли эти оценки доступны на момент покупки.

### 3. Собери препроцессинг

| Тип признаков | Преобразование |
|---|---|
| Числовые | Прочитать `NULL` как пропуск, заполнить медианой по train, затем стандартизовать через `StandardScaler`. Масштабирование особенно важно для KNN, где прогноз зависит от расстояний. |
| Категориальные | Заменить пропуски отдельной категорией, объединить редкие значения по частотам на train и применить one-hot с обработкой неизвестных категорий. Это особенно полезно для `Model` и `SubModel`, где сотни значений. |

В `sklearn` это удобно собрать через `ColumnTransformer` внутри `Pipeline`. Вызови `fit` только на train. При прогнозе на validation и test пайплайн применит уже рассчитанные медианы, масштабы и правила кодирования. Для `GaussianNB` понадобится плотная матрица, поэтому объединение редких категорий поможет сдержать её размер.

### 4. Зафиксируй базовый результат

Обучи три модели и сравни их на validation по Gini, используя вероятности `IsBadBuy=1`. По заданию достаточно, чтобы **хотя бы одна** модель набрала Gini ≥ 0,15. Затем можно добавить, например, отношение `VehBCost / MMRAcquisitionAuctionAveragePrice` и проверить, улучшилось ли качество. Для нулевой или отсутствующей оценки оставь результат пропущенным. Если добавишь среднюю цену по марке или модели, посчитай её по train и используй те же значения для validation и test.
